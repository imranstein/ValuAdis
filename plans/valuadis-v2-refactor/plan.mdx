# ValuAdis v2 — Hardening, Modular Refactor, Scraper Program & Enhancement Catalog

Ship the ValuAdis core to production on the current FastAPI + Nuxt stack, stage it on cPanel for testing, and run a test-driven in-place modularization ("v2") that never breaks the `/api/v1` contract — while bringing the web-scraper subsystem from unproven (0/8 E2E) to reliable, monitored, production-grade. A full improvements & enhancements catalog (UX + system) is included with priorities.

<Callout id="decisions" tone="decision">

**Decisions locked (2026-07-12):**
1. **Stack: keep FastAPI** — Laravel rejected for this cycle (full reasoning below).
2. **cPanel = staging/testing environment**; production runs on the already-scripted Docker VPS stack, which is also the only place the Playwright scrapers can run.
3. **v2 shape: in-place strangler refactor** into `backend/app/modules/` — no duplicated `v2/` folder.
4. **Scrapers are in scope** and get their own hardening program (Phase S below) with a staged rollout: one source proven end-to-end at launch week, the rest following per-source.

</Callout>

## Why not Laravel — the concrete issues

The attraction of Laravel is real but narrow: PHP deploys on any cPanel with zero setup. That is the *only* axis where it wins, and this repo has already neutralized it — [CPANEL_APP_DEPLOYMENT.md](../../CPANEL_APP_DEPLOYMENT.md) deploys the current FastAPI backend on cPanel using the built-in **Setup Python App** (Phusion Passenger) feature, no root access needed. So "easily hosted on cPanel" is true for the current stack today.

What a Laravel rewrite would cost, concretely:

    ["Scrapers (now in scope!)", "Playwright (Python) drives real browsers", "PHP has no first-class Playwright; Panther/chrome-php are far weaker. Rewriting scrapers in PHP makes your scraper goal harder, not easier"],
    ["ML valuation", "scikit-learn models + feedback-training loop", "No PHP equivalent; would need a separate Python service anyway — so PHP wouldn't even remove Python from the stack"],
    ["PDF certificates", "ReportLab + QR, proven output", "Re-implement in dompdf/snappy and re-verify layouts"],
    ["Background work", "Planned as a worker container on the VPS", "Laravel queues need Redis + supervisor — exactly what shared cPanel doesn't give you, so Laravel gains nothing here either"],
    ["User-visible benefit", "—", "None. The frontend stays Nuxt either way; users cannot tell what language serves the API"],
  ]}
/>

<Callout id="laravel-verdict" tone="risk">

**Bottom line:** the rewrite would spend 2–3 months to arrive exactly where we already are, minus the tests, minus PostGIS confidence, and with a *worse* scraper toolchain — while the deadline is measured in days. If PHP-nativeness ever becomes strategically decisive, the right moment is after v2 modularization, when each domain is a clean portable module. It is not now.

</Callout>

## Architecture

v2 is a **strangler refactor inside the existing app**: one domain at a time is rebuilt into a clean, fully-tested module under `backend/app/modules/`, old flat files are deleted as each module lands, and `/api/v1` never changes shape. Git tags (`v1-baseline`, `v2-complete`) mark the boundary. The scraper worker becomes a separate container sharing the same database and codebase.

**Hosting model:** cPanel hosts the **staging/testing** deployment (Setup Python App + static Nuxt, per the repo's existing guide) — good for tracing, UAT, and demoing. **Production** runs the Docker VPS stack (`docker-compose.prod.yml`, `deploy.sh`) because the scraper worker needs Playwright, a scheduler, and headless-browser dependencies that shared cPanel cannot run. Same code, two targets, both already scripted.

## Delivery model — TDD with subagents

Every Phase 1/2/3/S checklist item becomes one subtask JSON under `.tmp/tasks/` (existing repo convention) carrying: owned files, acceptance criteria (the failing tests to write first), and done-gates. Execution per subtask: **test-engineer agent** writes failing tests → **coder agent** implements to green → **code-reviewer agent** checks the diff against project rules → orchestrator runs the full gate (pytest ≥ 214 baseline, contract diff clean, typecheck, build) before merge. Disjoint-file subtasks run in parallel; `modules/auth` runs alone at the end. Scraper subtasks use fixture-based tests so CI never depends on live target sites.

<Callout id="tdd-gate" tone="info">

Invariant: **nothing is "done" on claim.** Done = gate ran and passed; for UI tasks the flow was clicked in a browser; for scraper tasks a scheduled run produced verifiable rows and run-history records.

</Callout>
