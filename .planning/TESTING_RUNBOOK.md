# Testing Runbook — Performance & Security

## Purpose

This runbook helps developers interpret test reports, triage failures, and take corrective action. Reference this before escalating a CI failure or opening a performance regression bug.

---

## Part 1: Interpreting Performance Reports

### 1.1 E2E Performance Report (`tests/e2e/performance-report.json`)

The file is generated by `performance.helpers.ts` after each Playwright run. Structure:

```json
{
  "run_at": "2026-03-22T10:00:00Z",
  "flows": [
    {
      "name": "login-flow",
      "page_load_ms": 1240,
      "api_response_ms": 180,
      "duration_ms": 3400,
      "status": "pass"
    }
  ],
  "summary": {
    "total": 8,
    "passed": 7,
    "failed": 1
  }
}
```

**Reading the report:**

| Field | Meaning |
|-------|---------|
| `page_load_ms` | Time from navigation start to page interactive |
| `api_response_ms` | Time for the primary API call in that flow |
| `duration_ms` | Total wall-clock time for the full flow |
| `status` | `pass` = within threshold, `fail` = exceeded threshold |

**Triage steps for a `fail` status:**

1. Check if failure is consistent across multiple runs or isolated — flaky timing on CI is common.
2. Compare `page_load_ms` against the baseline in `PERFORMANCE_TESTING_STANDARDS.md`.
3. If the threshold is exceeded by < 15%, re-run once. If it persists, investigate.
4. If exceeded by > 15%, treat as a regression — do not re-run to hide it.

### 1.2 k6 Load Test Report

k6 outputs to stdout by default. CI captures it as an artifact. Key metrics to read:

```
http_req_duration.............: avg=210ms  min=95ms   med=185ms  max=1.2s   p(90)=380ms p(95)=480ms
http_req_failed...............: 0.12%  ✓ 0         ✗ 3
checks........................: 98.5%  ✓ 394        ✗ 6
```

**What each metric means:**

| Metric | What to look at |
|--------|-----------------|
| `p(95)` | 95th percentile — primary threshold. Must stay under value in `endpoints.yaml` |
| `http_req_failed` | Percentage of requests that errored. Must be < 1% |
| `checks` | Custom assertions in the script (e.g., status == 200). Must be > 99% |
| `avg` | Average — informational only. Do not use as threshold |

**Triage steps for k6 threshold failure:**

1. Identify which endpoint failed — k6 groups by URL pattern.
2. Check if the failure is p(95) or error-rate based.
3. For p(95) failures: check if a recent DB migration, new middleware, or N+1 query was introduced.
4. For error-rate failures: check backend logs for 500 errors, check if auth tokens in the test are still valid.
5. Run the test in isolation against a local server to confirm it is not a CI environment issue.

### 1.3 Regression Investigation Checklist

When a performance regression is detected:

- [ ] Is the regression present locally or only in CI?
- [ ] Did any new middleware get added to the affected route?
- [ ] Was a new ORM query added that could produce N+1 queries?
- [ ] Did any external service call get added to the request path?
- [ ] Did bundle size increase significantly (check Vite build output)?
- [ ] Were any lazy-loaded components changed to eagerly loaded?

## Part 2: Interpreting Security Reports

### 2.1 npm audit Report

Generated by `npm audit --json`. CI fails on `critical` severity.

```
found 3 vulnerabilities (1 moderate, 1 high, 1 critical)
```

**Triage steps:**

1. Run `npm audit --audit-level=critical` locally to see the full advisory.
2. For each critical/high finding:
   - Check if the vulnerable package is a direct dependency or transitive.
   - If transitive: run `npm audit fix` — this resolves most cases automatically.
   - If direct: check if a patched version is available. Update `package.json` and test.
   - If no patch exists: assess exploitability in context (e.g., a CLI-only package used in build tooling vs. a runtime dependency).
3. Document the finding and resolution in a PR comment.

### 2.2 Bandit Python Security Report

Generated by `bandit -r backend/`. Output format:

```
Issue: [B608:hardcoded_sql_expressions] Possible SQL injection via string-based query construction.
Severity: HIGH   Confidence: MEDIUM
Location: backend/app/db/queries.py:42
```

**Triage steps:**

1. Open the flagged file and line number.
2. Determine if the finding is a true positive or false positive.
   - True positive: fix using parameterised queries or ORM methods.
   - False positive: add a `# nosec B608` inline comment with a justification comment above it.
3. Never suppress findings without a written justification in the same commit.

### 2.3 OWASP E2E Test Failures

Tests in `tests/e2e/security-owasp.spec.ts` fail with descriptive assertion messages.

**Common failure patterns:**

| Failure message | Likely cause |
|-----------------|--------------|
| `Expected to redirect to /login` | A route lost its auth middleware guard |
| `Expected 401, got 200` | An endpoint was made public accidentally |
| `Tampered token not rejected` | JWT verification middleware bypassed or misconfigured |
| `XSS payload rendered unescaped` | Template or component missing output encoding |

**Triage steps:**

1. Run the failing test in headed mode to observe the browser: `npx playwright test --headed tests/e2e/security-owasp.spec.ts`
2. Identify which OWASP category the failing test belongs to (test file is grouped by category).
3. Check recent changes to auth middleware (`frontend/app/middleware/auth.ts`) or backend route guards.
4. Fix the root cause — do not modify the test assertion to make it pass.

### 2.4 Security Unit Test Failures

Tests in `tests/unit/auth.security.test.ts`, `validation.security.test.ts`, `session.security.test.ts`.

**Triage steps:**

1. Run the single failing test with `--reporter=verbose` to see the full assertion output.
2. Check if a recent change to `useAuth.ts`, backend schema validators, or session handling caused the failure.
3. Security unit tests must not be modified to accommodate broken behaviour — fix the implementation.

## Part 3: CI Workflow Reference

The `.github/workflows/security-scan.yml` workflow runs on every PR and includes:

| Step | What it does | Blocks merge on failure |
|------|-------------|------------------------|
| `npm audit` | Scans JS/TS dependencies | Yes (critical only) |
| `bandit` | Scans Python code | Yes (high severity) |
| `safety` | Scans Python requirements | Yes (critical CVEs) |
| `playwright security` | OWASP E2E tests | Yes |
| `k6 load test` | API performance thresholds | Yes |

**If CI is blocked and it is an emergency:**

1. Get explicit approval from the tech lead.
2. Create a follow-up ticket for the suppressed finding before merging.
3. Never use `--ignore-advisories` or disable a test permanently without a ticket.

## Part 4: Quick Reference Commands

```bash
# Run all security unit tests
npx vitest run tests/unit/auth.security.test.ts tests/unit/validation.security.test.ts tests/unit/session.security.test.ts

# Run OWASP E2E tests
npx playwright test tests/e2e/security-owasp.spec.ts

# Run performance E2E tests
npx playwright test tests/e2e/phase1-foundation.spec.ts

# Run k6 load test (local)
k6 run tests/performance/k6-load-test.js

# Full dependency scan
bash scripts/scan-dependencies.sh

# View last performance report
cat tests/e2e/performance-report.json | jq '.summary'
cat tests/performance/baseline.json | jq '.'
```
